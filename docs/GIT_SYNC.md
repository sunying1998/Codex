# Git 同步与 Windows 日常使用

## 更新链路

开发者在云端修改源码、测试、提交并推送到 `sunying1998/Codex` 的 `main`。Windows 电脑通过 `Update-Yingke.cmd` 获取已提交版本、构建并重新启动。云端未提交或未推送的编辑不会自动出现在本机。

Git 只同步源码、文档、依赖锁文件与启动脚本。账号、项目、原始素材、导出结果及本机配置不进入仓库。浏览器访问的是本机服务，当前仅监听回环地址，未公开部署。

## 配置一次，之后双击更新

需要代理访问 GitHub 的 Windows 安装，在使用指定代理和 TLS 后端的新版接入器完成一次切换后，会保存本项目的 `.data/git-connection.json`。例如 Sakuracat 的 HTTP/混合端口为 `12450`，该配置会记住 `http://127.0.0.1:12450`、OpenSSL 和 HTTP/1.1。配置仅留在本机，不写全局 Git 设置，不保存认证信息；以后项目里的 `Update-Yingke.cmd` 自动读取它。

日常只需要打开 Sakuracat，再双击 `yingke-studio` 文件夹里的 `Update-Yingke.cmd`。工具获取新提交、备份、更新依赖和构建、重启网页及 Worker，检查就绪后打开浏览器。无需重新下载接入器、解压或手动复制源码；没有新提交且依赖和构建有效时会复用它们。平时仅使用当前版本，运行 `Start-Yingke.cmd` 即可。

从旧版 `Start-Yingke-Windows.cmd` 切换时，先在旧窗口按 Enter 停止两项服务，再运行一次新版接入器。切换完成后使用项目里的 Start / Update / Stop 入口；托管版会在更新时管理自己的服务，不再要求保留旧启动窗口。旧 Worker 还在运行时，工具会停止并提示处理，不会杀掉其他 Node 程序。

如果 Sakuracat 端口之后改变，只需修改本机 `git-connection.json` 的 `proxy` 值。JSON 支持 `version: 1`、`proxy`、`tlsBackend`、`httpVersion`，代理限本机 HTTP/混合地址，TLS 后端限 OpenSSL/Schannel，保持证书验证开启。配置无效或代理未启动时会给出明确错误；获取代码失败发生在停服之前，可以继续使用原来的版本。云端环境不读取这份 Windows 网络配置。

## 已有解压版：只迁移一次

1. 等当前处理任务结束，关闭旧的一键启动窗口或开发服务。
2. 双击为本机目录生成的一次性 Git 接入器。它检查 Node.js 24+、Git、FFmpeg；缺少时通过微软 WinGet 的 `winget` 源安装，保留安装包校验。需要 GitHub 登录时由 Git Credential Manager 的浏览器流程处理，不把密码或 token 写进脚本。
3. 接入器初始化隔离的临时仓库，通过 `fetch` 获取 `main` 并验证固定的安装器提交；随后备份原代码和数据库，把现有目录接入 Git。账号、素材、`.env.local` 等保留在原位置，其他未冲突的文件保留。接入后从已下载的临时仓库导入提交，验证来源、固定提交、分支历史及文件树，再快进合并，不重复连接 GitHub。
4. 首次构建通过、网页响应正常且 Worker 已就绪后，自动打开浏览器。之后只使用项目文件夹中的命令入口。

接入器根据原项目目录生成，无需把项目移到其他文件夹。它不会覆盖已存在的 Git 元数据；已经接入的新版本会直接运行正常更新。无法识别的已有 Git 配置会停止，交由本地任务处理。

迁移时关闭原启动器是必要步骤。迁移完成后，用项目文件夹里的 `Start-Yingke.cmd` 启动网页与 Worker；不同时运行旧启动器。启动入口会在构建和服务检查通过后打开浏览器。

旧解压版的入口可能名为 `Start-Yingke-Windows.cmd`。如果它已经显示 `READY`、`Keep this window open` 和 `Press ENTER to stop both services`，说明这次旧启动流程的网页及 Worker 已通过自检，需保持该窗口打开，按 Enter 会停止两项服务。这与后台托管版 `Start-Yingke.cmd` 的窗口行为不同；已有服务正常运行时，可先继续测试，不要再开启另一套启动器。

如果日志已经显示“已接入 Git”，之后检查更新失败或启动未完成，代码已在本机，可直接运行 `Start-Yingke.cmd` 重试准备和启动，无需重新下载安装器、解压项目或删除 `.data`。这个入口不检查 GitHub 更新；首次安装 npm 依赖仍可能联网，首次构建可能需要等待。只有要同步新代码时才运行更新入口。

供开发者生成接入器：

```bash
node scripts/create-windows-installer.mjs "C:\\path\\to\\yingke-studio" /tmp/Connect-Yingke-Git.cmd
```

生成前先提交并推送当前代码；脚本固定到该提交，避免首次启动执行未经固定的临时版本。生成的 `.review.ps1` 可供审阅，不需要单独执行，不修改 PowerShell 执行策略。

已知本机 HTTP/混合代理端口时，可为这个入口指定地址；遇到 Git Windows Schannel 握手中断时，可显式选择 Git 自带的 OpenSSL 后端：

```bash
node scripts/create-windows-installer.mjs "C:\\path\\to\\yingke-studio" /tmp/Connect-Yingke-Git.cmd http://127.0.0.1:12450 openssl
```

端口应以代理软件实际设置为准。该入口先检查端口，再验证仓库访问；TCP 端口响应不代表代理协议和 GitHub TLS 已成功。代理、HTTP/1.1、TLS 后端和启用证书校验的选项以进程级参数应用，保留原认证助手，不写全局或项目 Git 配置。成功准备后，选择保存到本机 `.data/git-connection.json`；后续 `Update-Yingke.cmd` 自动读取该文件，每次通过命令级参数传给 Git。显式指定或保存了连接配置后，不自动退回直连。环境中本次接入器的显式选择优先于旧的本机配置，便于修正端口。

OpenSSL 是兼容尝试，不保证修复网络中断。若 Git 不支持此后端，或发生证书、认证和代理策略错误，安装器会停止并显示错误，不关闭验证。安装器文件内嵌可审阅的 PowerShell，启动命令只读取该文件，避免 Windows 单行命令长度限制；不修改执行策略。

## 日常双击操作

| 文件                  | 行为                                               |
| --------------------- | -------------------------------------------------- |
| `Start-Yingke.cmd`    | 使用已下载的版本启动；依赖或构建缺失时自动准备     |
| `Update-Yingke.cmd`   | 获取 `origin/main`，更新后启动并打开浏览器         |
| `Stop-Yingke.cmd`     | 通过认证的本机控制入口停止本项目托管进程           |
| `Status-Yingke.cmd`   | 显示网页与 Worker 是否已就绪                       |
| `Diagnose-Yingke.cmd` | 收集图片错误与编码信息，报告不包含原图、密码或会话 |

关闭启动命令窗口不停止后台服务。停止本机服务请使用停止入口。程序不注册开机自启或系统服务。

对应命令为 `npm run local:start`、`local:update`、`local:stop`、`local:status`。开发源码时使用 `npm run dev`，不同时运行第二个 Worker。

## 更新时实际发生的步骤

1. 检查仓库、`origin` 和当前 `main` 分支，检查已跟踪的源码是否有本地修改。
2. 获取远端提交，拒绝非快进更新、敏感数据路径、链接和子模块。
3. 通过本项目的本机控制入口停止托管的网页与 Worker；Worker 会把未完成任务重新排队。旧版或其他 Worker 仍运行时停止更新，不关闭其他 Node 程序。
4. 使用 SQLite 在线备份 API 保存一致的数据库快照，并备份本机配置与更新前提交信息；原视频保持在原目录。
5. 执行快进合并。依赖锁文件或 Node 主版本改变时运行 `npm ci`，代码提交改变或构建缺失时运行生产构建。
6. 后台启动网页与 Worker，检查网页和任务服务就绪，再打开浏览器。

不执行强制推送、`reset --hard`、`git clean` 或自动丢弃本地修改。未跟踪的个人文件保留；若它们与即将下载的文件冲突，Git 会拒绝合并。

## 备份、状态与失败处理

- `.data/updates/first-git-setup-*`：首次迁移前的旧源码与数据库、配置备份。
- `.data/updates/git-update-*`：更新前一致数据库快照、配置及 `version.json` 提交记录。
- `.data/runtime/`：本项目服务日志、运行控制状态、已安装依赖与构建记录。
- `.data/git-connection.json`：此电脑的 Git 代理和 TLS 偏好，更新时随本机配置备份。
- `.data/media/`：原视频、参考照片、缩略图和导出结果，更新不删除或搬移它们。

配置了 `YINGKE_DATA_DIR` 时，运行状态和更新备份使用该持久化目录。旧代码备份和数据库配置包含私人数据，应保留在本机，不提交到 Git。自动更新备份不重复复制大型媒体，不代替 README 中的完整备份流程。

如果本地代码有修改或分支分叉，更新会在停服前停止，先处理 Git 状态。网络获取失败也会保留运行中的版本。

遇到“本地受 Git 管理的文件有修改”时，新版入口会列出文件名及状态；安装器在下载前检查，避免反复联网后才停止。先检查具体文件，再决定如何保留或合并，不自动丢弃修改或清理个人文件。旧版启动器或开发工具也可能修改依赖及生成配置，仅凭这条提示不能认定这些改动可以删除。

可生成独立只读检查入口供尚未更新的 Windows 安装使用：

```bash
node scripts/create-windows-git-check.mjs "C:\\path\\to\\yingke-studio" /tmp/Check-Yingke-Local-Changes.cmd
```

该入口不联网、不启动或停止服务，只显示当前提交、分支、已跟踪文件的状态及增删行数；不打印文件内容、认证信息或未跟踪的素材列表。Git 使用 `--no-optional-locks`，差异统计禁用外部 diff 和 textconv；不会还原、暂存、stash、提交或删除文件。它可以从下载目录直接运行，无需复制进项目。确认变更来源后再继续同步。

构建失败时，新代码可能已经同步，服务保持停止；备份与之前的提交仍然保留。修复原因后再次双击更新即可重试。需要恢复旧版本时，根据备份中的提交信息处理，先保留现有数据；更新器不自动降级或覆盖数据库。

运行日志位于持久化目录的 `runtime/service-*.log`。旧启动器关闭后可能需要最多 30 秒等待租约过期，脚本会等待。若启动端口被其他程序占用，会尝试其他本机端口；不会关闭占用程序。

### Windows Git 指向未运行的本机代理

如果出现 `over proxy 127.0.0.1 ... Could not connect to server`，说明连接停在本机代理，尚未到 GitHub 认证阶段。接入器现在先用 `ls-remote` 检查实际访问。

仅当 Windows Git 明确报告回环代理连接失败时，工具会为该 Git 子命令临时尝试直连。代理环境变量只从该子进程移除，代理覆盖参数仅通过 `git -c` 传入；全局 Git、Windows 代理配置和认证助手保留，TLS 校验保持启用。正常代理、非回环代理、认证失败、证书错误和代理策略拒绝不会触发该重试。云端执行仍保留平台提供的代理路由。

首次接入成功选择直连后，同次安装的后续 Git 命令沿用这个进程内选择；不会写入 `.env` 或 Git 配置。之后的 Windows 更新也具有相同的连接诊断。若直连也失败，恢复原代理服务或修正其地址后重试，脚本会显示连接错误而非笼统要求登录。

### GitHub 连接被重置

`Recv failure: Connection was reset` 表示传输连接中断，单凭这一行不能确认中断来自代理、网络还是远端。Windows 接入器与更新器在 `ls-remote` 或 `fetch` 遇到该错误时，会沿用当前网络路径，以命令级 `http.version=HTTP/1.1` 重试一次；不会因为重置错误自动更换代理或关闭证书校验。首次接入选择的协议在同次安装的后续命令中沿用，不写入 Git 配置。克隆和推送不因重置自动重试，以免重复操作或碰到残留目录。

HTTP/1.1 是兼容尝试，不保证修复连接。如果仍失败，请确认原代理程序已启动、Git 的代理端口与软件当前监听端口一致，并检查浏览器能否访问仓库。浏览器访问成功不能证明 Git 使用同一代理；不要为此关闭 TLS 校验，也无需删除原项目或素材。

安装器的仓库预检查和 `fetch` 在连接被重置或 TLS 接收握手中断时最多尝试三次，始终保留所选代理、TLS 后端和证书验证。下载使用独立临时仓库中的 `fetch`，可在原临时仓库重试，不重复创建有残留目录的克隆。使用本机保存配置的日常更新同样最多尝试三次；未保存配置时沿用原有的一次兼容重试。证书拒绝、认证失败、取消和策略拒绝不重试。握手中断与证书验证失败分别报告，不能仅凭 `SSL/TLS connection failed` 认定为证书问题。

## 本机控制边界

控制入口仅监听回环地址，使用本机忽略目录中的随机凭据认证。更新器通过该入口管理自己启动的进程，不枚举并结束所有 Node 程序。Windows Worker 通过父进程 IPC 正常停机，避免仅终止父进程而留下视频处理子进程。
